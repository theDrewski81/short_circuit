## 2. Why this is a stop and not a work-around

The three scope items are individually harmless — two text edits and a read-only probe — and
none of them touches a file S19's block touches. It would have been technically possible to do
them anyway.

It is still the wrong call, for a reason specific to how this project hands over git writes.
D7's own deliverable is a command block for Andrew, cut against `main`. The brief specifies
`docs/drawing-and-figure-fixes` created off `main`. If S20 had branched off `main` at `ebdea9e`
and S19's block were run afterwards, `fix/pi-m-bringup` would also be cut from `ebdea9e` and the
two branches would land in an order nobody chose, with `main` briefly carrying a documentation
revision while still missing the Pi-M fix that the state document already records as closed.
The brief anticipated this, which is why the precondition exists and why it says stop rather
than proceed with care.

The second reason is smaller and concrete: adding S20's edits to a working tree that already
holds S19's three uncommitted files puts five uncommitted files in front of Andrew at once,
belonging to two sessions, with two separate command blocks to keep straight. S19's block uses
explicit paths in its `git add`, so it survives the extra files — but the confusion is the cost,
and it is avoidable by running one block before starting the other.

little width and buys a reader the ability to check any single row.

**The system Python version is recorded as an absence, not filled in with 3.13.** It is the
obvious inference and it is probably right. It is also precisely the kind of plausible
correlation `docs/ORCHESTRATION.md` section 9 says produced three separate failures in this
project. The document says what is known, says what is expected, and says which is which.

**The overlay was not attempted, and the document says why in the project's own words.** The
brief instructed this. The document goes one step further and specifies the shape the overlay
section should take when someone writes it, so the next session inherits a template rather than
a blank heading.

**No `setup_vision_pi.sh` was written.** Out of scope by the brief, and I would recommend
against writing it in a later session too, for a reason the brief did not raise. See section 5.

**The unverified list is a section of its own rather than a scatter of caveats.** Caveats
distributed through a document get read past. `PROJECT_STATE.md` section 3's Phase 01 caveat is

## 5. Open threads discovered

**1. Nothing provisions Pi-V, and writing the script blind would repeat O15.** This is the
asymmetry the brief asked me to raise, plus a recommendation the brief did not ask for.
`setup_vision_pi.sh` could be written today from `phases/PHASE_01_INFRASTRUCTURE.md` task 2 and
`.env.example`. It could not be tested, because no session can reach `192.168.1.218`. That is
exactly the position O15 is in: `setup_motion_pi.sh` was corrected at S19, is believed right,
and has sat open for two days as fixed-not-closed because nobody has run it on the box.
Writing a second untested provisioning script would double that debt to buy a file. **My
recommendation is to defer it to a Pi-V bringup session and write it there, against the
hardware, the way `setup_motion_pi.sh`'s corrections came out of the 2026-07-12 bench work.**
If Andrew would rather have it now as a checklist he can follow by hand, a numbered runbook in
this document is a smaller and more honest deliverable than a script that has never run.

**2. `.env.example` carries what appears to be a live API key, and the repository has a GitHub
remote.** `LITELLM_API_KEY=sk-ft-osuRqKu2Eldav3HgAVw` is a literal value, not a placeholder,
and the surrounding comment says the key was minted on the AOS LiteLLM proxy on 2026-06-22 for
this project. Every other secret in that file is a placeholder: `MQTT_PASSWORD` is
`<set-on-broker-deploy>`. The file is tracked and the remote is
`https://github.com/theDrewski81/short_circuit.git`. **I have not checked whether that
repository is public and cannot from here.** If it is, the key is exposed and has been since
2026-06-22; if it is private, the key is still committed to history and will be exposed by any
future decision to open the repository. **Recommendation: rotate the key on the AOS proxy and
replace the value in `.env.example` with a placeholder.** Rotation matters more than the file
edit, because the value is already in git history and editing the file forward does not remove
it. This is outside my scope, I have not touched the file, and it is the most consequential
thing in this report.

**3. Hardware PWM on Pi-V is unrecorded.** `BOM.md` puts the 1 W navigation light on Pi-V
GPIO13 as a hardware PWM output into a MOSFET gate, and `docs/HARDWARE_power_harness.md`
carries the same net as `SIG_NAV_PWM`. On Pi-M, hardware PWM needed an explicit
`dtoverlay=pwm-2chan,...` line and a reboot before `/sys/class/pwm` existed at all, and the
failure without it looked like dead hardware rather than a configuration error. No equivalent
line is recorded anywhere for Pi-V. Whether one is needed, and whether it coexists with the
I²S assignment on the same header, is not answered by any file in this repository. Recorded in
the document as an absence. It belongs with O1, since both are `config.txt` questions about the
same box, and both should be settled at a Pi-V bringup rather than reasoned about from here.

**4. The Phase 04 camera guidance names a different OS than the box runs.**
`phases/PHASE_04_COGNITION.md` task 2 and its Known Constraints both say Bookworm and warn that
`picamera2` APIs differ between OS versions; `PROJECT_STATE.md` puts both Pis on Trixie. The
warning is sound and applies to the document that gives it. Not a defect worth a session on its
own, but worth folding into the next Phase 04 edit. Note also that the repository's only
working capture path uses `rpicam-still`, not `picamera2`, so the Phase 04 pipeline will be the
first `picamera2` code on this box.

**5. No systemd unit exists for either Pi.** Both `deploy_motion.sh` and `deploy_vision.sh`
restart a unit their own comments call TBD, and tolerate the failure. Symmetric, so not part of
the Pi-V asymmetry, but it means neither deploy script currently does the second half of its
job. Phase 05 territory.

**6. Pi-V has never had a bringup session.** Threads 1, 3 and 4, plus O1 and the whole
unverified list in the new document, close together at one session with the box in hand, the
way 2026-07-12 closed the equivalent set for Pi-M. That session is not dispatchable now: it
needs the audio hardware wired, which is not on the Phase 02 critical path and sits behind the

rediscovering when Phase 04 opens.

**7. Two unlogged commits on `main`.** `23157ef` and `ecb244f`, covered in section 1. Section 6

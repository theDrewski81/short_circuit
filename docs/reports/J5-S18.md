## 4. Decisions taken, with rationale

**The two verification scripts are not committed.** `check_vision_deps.py` and
`check_memory_index.py` prove definition-of-done items (b) and (f); they live outside the
repository and their output is pasted above. A guard is worth what its failures prove, and
both are shown above failing on the actual defect they exist to catch, so they would be
defensible additions. I left them out because the brief asked for a command that proves a
claim, not for a guard, and adding two uninvoked scripts to `scripts/` creates two more
things that can rot without anyone noticing. If they should be permanent, that is a
deliberate decision with a cost, and it is not mine to take inside this scope. Recommended
in section 6.

**`pyproject.toml` carries no `[build-system]` section.** Johnny 5 is deployed by copying
`src/` onto a Pi, not by installing a package. A build-system table would make the
repository look installable and invite someone to `pip install -e .`, which nothing here
supports. The file exists only to configure the tools that look for it, and says so.

**No `pythonpath` setting was needed.** Each file in `tests/` does its own
`sys.path.insert(0, ../src)`, so `testpaths` alone is sufficient. Adding
`pythonpath = ["src"]` would have created a second mechanism doing the same job, with the
tests still carrying the first.

**O8's premise is wrong in one detail, and the correction is recorded rather than papered
over.** `PROJECT_STATE.md` O8 and the brief both say `httpx` and `python-dotenv` are
imported by `src/vision/llm_client.py`. `llm_client.py` imports `httpx` only. `python-dotenv`
is imported by `scripts/test_llm_client.py` and `scripts/whats_this_color.py`, both of which
are Pi-V bench programs that drive that module. Both packages are still the right contents
for one Pi-V requirements file, so the deliverable is unchanged; the file states which module
needs which.

**The requirements file sits at `src/vision/`, beside the code it serves.** That is the one
existing precedent in this repository: `simulation/chassis/requirements-train.txt` sits with
`env.py` rather than at the root. The root already carries five loose notes this same session
was asked to look at, so adding a sixth root file would have been working against the item.

**Pinned exactly, and the pins are labelled as unverified.** `httpx==0.28.1` and
`python-dotenv==1.2.3` are the current PyPI releases as of 2026-08-25, which is what the
brief asked for and what a two-package runtime deserves. They have **not** been checked
against what is installed on Pi-V, which no agent session can reach. The file says so in a
comment and says that if a `pip install -r` on the Pi disagrees with a working install, the
Pi wins.

**`MEMORY.md` was made to match the files, not the reverse.** Renaming
`johnny5-cloud-mount-quirks.MD` and `johnny5-phase02-locomotion.MD` to `.md` is the tidier
fix and is impossible from here: the mount cannot delete or rename. It is also a git write
either way. The index now spells both as git spells them, which is the fix that survives
regardless of what happens to the files.

**`MEMORY.md` gained a header saying it is an index, not a summary.** Reading an index line
in place of the document behind it is the S14 failure, and this specific file is the one that
was read. The header points at `docs/ORCHESTRATION.md` section 9 and states that
`PROJECT_STATE.md` is the authority. The alternative — deleting the stale branch reference
and leaving the index otherwise inviting — fixes the instance and not the shape.

**The 1531 g figure was taken from the script that prints it, not from a document.**
`mechanical/preview/mass_budget.py` was copied out of the mount and run in a scratch
directory, because Python cannot import from the mounted repository. It printed
`ASSEMBLED TOTAL 1531 g (95.7% of ceiling)`, `headroom 69 g`,
`worst-case (+25% printed) 1578 g UNDER ceiling`. `mechanical/` was not modified. This
matters because that script crashed silently for two months and every mass figure quoted in
that window was produced by hand.

**The `BOM.md` mass entry was struck through, not deleted.** The file's open-items list
already uses `~~struck~~ — closed …` for resolved items, and the entry records a real reading
that a later rework superseded. Deleting it would leave a reader who finds 1655 g elsewhere
with nothing to reconcile it against.

**On the schematic, the substitution leaves a redundancy I did not extend the scope to
fix.** The wiring key's rows previously read `#5218 …` in the left column and `#5219 …` in
the right, so the part number was doing the work of telling the columns apart. With both
motors #5218 the column headers `LEFT motor #5218 (ch A)` and `RIGHT motor #5218 (ch B)` are
the only thing distinguishing them, and the per-row prefix is now redundant rather than
wrong. Changing those prefixes to `LEFT`/`RIGHT` would have touched six labels where the
brief named five. Left as an open thread in section 6.

## 5. O10 — do the loose notes belong in the repository?

**Recommendation: no, with one salvage first. Do not remove them until the salvage lands.**

The five files are exports from a Claude project-memory store: each carries YAML frontmatter
with `node_type: memory`, a `type`, and an `originSessionId`, and they cross-reference each
other with `[[wikilinks]]` that resolve to nothing on GitHub. They are agent scratch, and
they are a second state store with its own index sitting in a repository whose central lesson
is that a second state store with an index is how it fails.

Three of the five are already fully covered by documents that are in the mandatory read path,
and are pure duplication:

- `sandbox-no-torch.md` restates `docs/ORCHESTRATION.md` section 7, "The agent sandbox cannot
  install PyTorch", and `PROJECT_STATE.md` section 9's S07/S08 entry.
- `johnny5-cloud-mount-quirks.MD` restates the same section's truncation, `/tmp` and
  `md5sum` hazards.
- `feedback_conciseness.md` restates `CLAUDE.md`'s Token Discipline and Style sections.

Duplication is not the only cost. **`johnny5-cloud-mount-quirks.MD` states a git permission
the project has since withdrawn**: "the agent **may create/switch branches** as part of
delivering work". `CLAUDE.md` and `docs/ORCHESTRATION.md` section 6 now say every git write is
Andrew's, and this session's own brief says to run none. A note in the repository asserting a
wider permission than the authority grants is worse than a redundant one.

`johnny5-phase02-locomotion.MD` is mostly duplicated by `PROJECT_STATE.md` section 9 and
`simulation/chassis/TUNING.md`, and it opens with "Work on branch `sim/chassis-env`", a branch
deleted on 2026-08-23. It should be diffed against `TUNING.md` for anything unique before it
goes.

**`johnny5-pi-m-env.md` is the salvage, and it is not optional.** It holds Pi-M bringup facts
that exist nowhere else in the repository and that contradict a script that is in the
repository:

- The venv is at `~/johnny5-env`. `scripts/setup_motion_pi.sh` line 16 defaults to
  `${JOHNNY5_VENV:-$HOME/johnny5/venv}`, so re-running it without the override builds a
  second venv.
- `lgpio` cannot pip-build on Trixie with Python 3.13: no cp313 piwheel, and the sdist links
  against a system `-llgpio` that is not present. The fix used was
  `sudo apt install python3-gpiozero python3-lgpio` plus
  `include-system-site-packages = true` in `~/johnny5-env/pyvenv.cfg`.
  **`scripts/setup_motion_pi.sh` line 76 still does `pip install … gpiozero lgpio`**, which
  is the thing that fails.
- The `pwm-2chan` overlay needs `pin=12,func=4,pin2=13,func2=4` and a reboot before
  `/sys/class/pwm` populates. The script has this at line 22; the note adds that the default
  overlay maps to GPIO18/19 and why that matters.

That content belongs in `scripts/setup_motion_pi.sh` and in a Pi-M runtime section of
`docs/`, not in a root note nobody's read path includes. Until it is moved, removing the file
loses a live correction to a script Andrew will run again.

So: fold `johnny5-pi-m-env.md` into the script and the docs; diff
`johnny5-phase02-locomotion.MD` against `TUNING.md` and keep anything unique; then
`git rm` all five plus `MEMORY.md`. **I executed none of this.** The mount cannot delete, the
removal is a git write, and the salvage is a real piece of work rather than a tidy-up — it is
a queue item, not a footnote. `MEMORY.md` is left correct and self-warning in the meantime.

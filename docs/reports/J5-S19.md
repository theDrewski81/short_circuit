## 4. Decisions taken, with rationale

**The script reads `requirements-motion.txt` rather than keeping its own list.** S18 suggested
this and it is the point of O16: two lists drift, and the drift is exactly what produced O15 —
a note held the correction for six weeks while the script held the defect. The cost is that the
script must now be run from inside a checkout. It already had to be (`bash scripts/setup_motion_pi.sh`),
but the dependency is now hard, so the script fails early and loudly with a message naming the
missing file rather than dying inside pip. I deliberately did **not** write an inline fallback
list for the file-missing case; a fallback list is a second list, which is the thing being fixed.

**`gpiozero` and `lgpio` are removed from pip and added to apt, not pinned anywhere.** They are
distribution packages now; pinning a Debian package version in a pip requirements file would be
a lie about what installs them. `requirements-motion.txt` names them in a prominent comment
block with the apt command, so a reader who installs only from the file and then fails at bench
time has the answer three lines above the package list.

**The venv gets `--system-site-packages` on creation, and an existing `pyvenv.cfg` is repaired
in place.** The flag alone would have been half a fix: Pi-M's `~/johnny5-env` already exists and
was built without it, so on the box this defect is actually about, the new flag would never
fire. The `sed` only rewrites an explicit `include-system-site-packages = false`, so it is a
no-op on a venv that is already correct and safe to re-run.

**A `--system-site-packages` venv is a real trade and I am naming it.** It exposes every apt
Python package to the venv, not just the two wanted. On a Pi Zero 2 W running one application
that is a small cost, and it is the route the bench actually used and proved. The alternatives
are worse: a `.pth` file pointing at `dist-packages` is the same exposure by a less legible
mechanism, and building `liblgpio` from source on the Pi to make the pip sdist work adds a
compile step to a provisioning script for a package apt already has.

**The verification block now imports `gpiozero`, `lgpio` and `rpi_hardware_pwm` and prints where
each resolved from.** Previously it checked only onnxruntime. The system-site-packages link is
the fragile part of this fix and it fails silently — the venv activates, pip succeeds, and the
failure surfaces as an `ImportError` at the bench with the motors wired up. Printing the
resolved paths distinguishes "apt package visible through the venv"
(`/usr/lib/python3/dist-packages/...`) from "pip package in the venv" without asserting a
version attribute I cannot verify on a machine I cannot reach.

**`paho-mqtt` is declared even though nothing imports it yet**, and the file says so in those
words. `src/motion/main.py`'s MQTT functions are still Phase 01 stubs. Dropping it would have
been defensible and I chose against it: the script has installed it since Task 1, Task 6b's live
offline-fallback test is what will first need it, and a requirements file that silently drops a
package the previous line installed invites someone to reinstate it by hand.

**Pin style: floors, not exact pins, unlike `requirements-vision.txt`.** That file pins exactly
and explains why. Pi-M is different in one way that matters: it installs from the piwheels
mirror, whose available versions can lag PyPI, so an exact pin risks being unsatisfiable on the
target for a reason that has nothing to do with the project. `numpy<3` copies
`requirements-train.txt`'s ceiling rather than inventing a different one. The file states
plainly that none of this is verified against Pi-M.

**The new document is `docs/HARDWARE_pi_m_runtime.md`.** The `HARDWARE_` prefix groups the two
existing Pi-side reference documents and this is the third; it covers the device-tree overlay
and GPIO access, which are hardware enablement. The counter-argument is real — venv paths and
pip packages are not hardware — and `docs/PI_M_RUNTIME.md` would have been defensible. I chose

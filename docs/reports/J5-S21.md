### The CR check, and what can and cannot be run before the commit

The brief requires the CR count read from the object database rather than through
`git diff --ignore-cr-at-eol`. The blobs do not exist yet, because this session makes no git
writes. What can be established now is that the bytes on disk are CR-free and that git's
clean filter will not add any:

```
$ for f in .gitignore docs/HARDWARE_drive_bringup.md docs/diagrams/bench_full_schematic.svg; do
      printf '%-45s CR=' "$f"; tr -cd '\r' < "$f" | wc -c; done
.gitignore                                    CR=0
docs/HARDWARE_drive_bringup.md                CR=0
docs/diagrams/bench_full_schematic.svg        CR=0
```

and, comparing the hash git would store for each file against the hash of its raw bytes:

```
$ for f in .gitignore docs/HARDWARE_drive_bringup.md docs/diagrams/bench_full_schematic.svg; do
      a=$(git hash-object --path "$f" --stdin < "$f")
      b=$(git hash-object -t blob --stdin < "$f")
      [ "$a" = "$b" ] && echo "$f  $a  filter is a no-op"; done
.gitignore                                     dcdcb362d6e214d153c105f21d60d583ed065547  filter is a no-op
docs/HARDWARE_drive_bringup.md                 e1714a694946f30900a5c1fa50e1a6f594c4be96  filter is a no-op
docs/diagrams/bench_full_schematic.svg         4edea5009d5178657d4c612eb3848e6c8978a3d6  filter is a no-op
```

`git hash-object --path` applies the clean filter; the bare form does not. The two agreeing
means the filter changes nothing, so the blob will be byte-identical to the file on disk,
which has no CR in it. Neither form writes to the object database; `-w` was not used.

**The object-database check itself is in section 6's block for Andrew to run after the
commit**, in the `cmd`-redirect form `docs/ORCHESTRATION.md` section 6 prescribes for
PowerShell, because a PowerShell pipe strips line endings and would read 0 whatever the

**Line 73's clarification sits on one long line rather than being wrapped.** The
definition of done is `grep -n 1807 ...` returning two lines "each now naming 451.74 and

following line would satisfy a reader and fail the check. The surrounding prose in that

carrying the figure is long. Markdown renders it identically. If the orchestrator would
rather have the wrapping than the grep, that is a one-line change and the check needs

**`BOM.md`'s wording was reused almost verbatim rather than paraphrased.** O19 asks for "the
same clarifying half-sentence `BOM.md` got at O14". Two documents that state the same
correction in different words are how a project ends up with two figures again; the point
of the item is that a reader who meets 1807 in either file gets the same sentence. The one
deviation is "the `gpiozero.RotaryEncoder` decode below is 1×" in place of `BOM.md`'s
"`gpiozero.RotaryEncoder` decodes 1×", because in this file the decoder is named again two
sentences later and the cross-reference is worth making explicit.

**`.gitignore` was normalised to LF as part of the O20 edit.** Its working-tree copy was
CRLF throughout while its tracked blob is LF, and `core.autocrlf = input` would have
stripped the CRs at commit either way, so the committed result is identical. Normalising
means the file this session hands over is verifiably CR-free on its own bytes rather than
CR-free only because a filter is expected to run, which is the distinction
`docs/ORCHESTRATION.md` section 9 records a past defect against. The blob is unchanged for
all 24 pre-existing lines, so the commit's diff is the two added lines and nothing else,
which the hash comparison in section 3 demonstrates.

**The `.gitignore` entry got a comment naming `PROJECT_STATE.md` section 6.** One bare line
would have closed O20. A future reader who finds `.claude/` in `.gitignore` and wants to
know whether that was deliberate now has one hop to the answer, and section 6 is the place
that answers it.

**`ORCHESTRATOR_PROMPT.md` was left alone.** `PROJECT_STATE.md` section 6 lists it in the
same row as `.claude/` as deliberately untracked, so it is the obvious second line to add.
O20 names `.claude/` only, and widening a cosmetic item mid-session is how scope creeps.
Reported in section 5 instead.
